Исходники приложения не изменялись. Проверки выполнялись с локальными stub-провайдерами и SQLite в памяти, без платных LLM-вызовов и изменения рабочей базы.

## Назначение и особенности

Это экспериментальный стенд координации LLM с распределённой информацией. Каждый агент получает общую задачу и собственные закрытые факты. Обсуждение последовательно; scheduler выбирает следующего участника. После обсуждения назначенный proposer формирует предложение, все агенты независимо голосуют по одному замороженному артефакту, затем детерминированный evaluator проверяет принятое решение.

`ExperimentRunner` используется CLI, HTTP и batch-запусками. `LlmCaller` централизует обращения к моделям, повторы, учёт usage и trace. SQLite хранит конфигурации, события и производные summaries. Presentation, человеческие вопросы после запуска и внешние комнаты вынесены в отдельные слои.

Сильные стороны:

- консенсус отделён от правильности;
- закрытая информация не включается в prompt маршрутизатора;
- предложение фиксируется с hash, голосование использует одинаковый transcript;
- готовность агента устаревает после новых сообщений других участников;
- trace сохраняет prompts, ответы, попытки, маршрутизацию и версии;
- stub-запуски позволяют проверять движок без сети;
- есть существенное регрессионное покрытие границ ядра и дополнений.

Это стенд конкретного протокола согласования, а не универсальная среда автономных агентов: инструменты зарезервированы, proposer фиксирован, память в основном представлена transcript, встроенных независимых задач фактически две — Space Station и Cascade. Kestrel использует задачу Space Station с другим поведением и представлением.

## Подтверждённые существенные дефекты

Уровень P0 не подтверждён: оснований заявлять RCE, полный обход авторизации или массовое уничтожение данных нет. Ниже — major-дефекты доступности, целостности и исследовательских результатов. У каждого указаны условия проявления.

### 1. P1: некорректный URL завершает сервер до авторизации

Код: `src/server/app.ts:551`, `src/server/externalApp.ts:162`.

`new URL(req.url, ...)` вызывается в синхронном callback HTTP-сервера до защищённого `try/catch`. Запрос с request-target `//[` вызывает `ERR_INVALID_URL`, который выходит наружу и завершает Node-процесс. Токен до этого не проверяется.

Подтверждение: локальный listener External API с заданным токеном получил без авторизации `GET //[ HTTP/1.1`; процесс завершился с кодом 1 и `TypeError: Invalid URL`. В operator listener стоит тот же незащищённый вызов.

Последствие: потеря всех выполняющихся в процессе экспериментов. Эксплуатация требует доступа к listener; по умолчанию operator UI доступен на loopback. При прямом сетевом доступе к External API дефект удалённо достижим; поведение reverse proxy может ограничивать доставку такого URL.

Правка: включить разбор URL в обработку ошибок обоих listener, некорректные request-target отклонять с HTTP 400. Регрессионный тест должен отправлять сырой HTTP-запрос без токена и проверять, что последующий корректный запрос обслуживается.

### 2. P1: batch-путь позволяет менять Object.prototype даже при отклонённой конфигурации

Код: `src/batch/spec.ts:117`, особенно строки 130 и 133–134.

`setAtPath` использует `key in container`, поэтому проходит по унаследованному `__proto__`, затем записывает значение в общий `Object.prototype`. Валидация выполняется уже после изменения. `structuredClone(base)` не защищает прототипы объектов от такого обхода.

Подтверждение: `BatchService.resolve` для переменной `{path: "__proto__.auditMarker", values: ["polluted"]}` бросил `BatchValidationError`, но после этого `({}).auditMarker` вернул `"polluted"`.

Последствие: отвергнутый batch способен менять унаследованные значения для других объектов и последующих запусков в том же процессе. Это нарушение изоляции условий эксперимента и безопасности импорта конфигураций. Доступ к operator API при включённой авторизации требует токена; обход токена этим воспроизведением не установлен.

Правка: до любых изменений проверять все сегменты пути; запрещать `__proto__`, `prototype`, `constructor`; для промежуточных узлов использовать `Object.hasOwn`; отдельно проверять индексы массивов и `*`. Проверка должна покрывать все пути batch до построения первого условия. Добавить тест отсутствия изменений глобального прототипа после отказа.

### 3. P1: Cascade принимает процедуру, нарушающую временной дедлайн

Код: `src/scenarios/kestrelCascade/evaluator.ts:132`, `:152`.

Время эвакуации сравнивается с аварийным окном только при использовании thermal dump C. Временная стоимость действий до запуска loop B не учитывается.

Подтверждение: при стандартных параметрах, где эвакуация занимает 6 минут, а безопасное окно равно 4 минутам, последовательность ниже получает `SUCCESS` и пустой список нарушений:

```text
evacuate_r3 → isolate_r3 → switch_beacon_to_battery
→ shutdown_research_labs → shutdown_external_communications
→ route_power_to_loop_b → start_loop_b → scram_reactor
```

Эвакуация и изоляция завершены до охлаждения, следовательно loop B запускается после дедлайна. Это ложноположительный результат основного научного измерителя.

Правка: вычислять состояние и истекшее время по порядку действий, проверять дедлайн достижения работоспособного охлаждения для любого пути. Как минимальный шаг — учитывать длительность эвакуации, если она предшествует запуску охлаждения. Явно определить длительности и возможность параллельных действий; добавить позитивные и негативные контрольные планы. После изменения семантики поднять версию evaluator.

### 4. P1: финальное голосование обходит проверку token/cost cap

Код: `src/experiment/runner.ts:455`, `:690`.

Перед голосованием лимиты проверяются, после `runVoting` успешный consensus сразу переходит в evaluation. Нет проверки лимитов на завершении последнего шага. Аналогично последний отказ в консенсусе может завершиться без бюджетного outcome.

Подтверждение на штатном cooperative stub: `totalTokenCap = 12914`, фактическое потребление `18384`, результат `SUCCESS`. Cap выбран на один токен выше потребления до голосования.

Документированный overshoot одного шага сам по себе допустим. Дефект состоит в том, что превышение не получает предусмотренный budget outcome и detail: итоговые показатели успеха учитывают запуск вне его бюджета. `totalCostCapUsd` проходит через ту же отсутствующую проверку; денежный overshoot отдельно не измерялся.

Правка: проверять лимиты после завершения шага, до commit/evaluation и до окончательных terminal branches. Сохранять уже полученные голоса и usage, затем применять явно заданный приоритет бюджетного исхода. Проверить успешное и неуспешное финальное голосование. Для финансовой защиты дополнительно проверять известный расход перед повторными запросами; жёсткой гарантии расходов при неизвестной цене и уже запущенных запросах это не даёт.

### 5. Major, условие — ошибочное дополнение: onRunEnded может переписать outcome

Код: `src/experiment/runner.ts:335`, `src/experiment/extensions.ts:75`.

В `onRunEnded` передаётся ссылка на исходный `outcome`. В отличие от опубликованных сообщений, объект не клонируется и не замораживается. Extension может присвоить `info.termination.outcome` новое значение, которое затем попадёт в `finish`.

Подтверждение: extension заменил `SUCCESS` на `MISSION_FAILURE`; сохранённые метрики содержат `evaluation.outcome = SUCCESS`, `termination.outcome = MISSION_FAILURE`, `extensionErrors = 0`.

Это прямое нарушение заявленного архитектурного контракта. Встроенное дополнение, которое сейчас так делает, не найдено; дефект относится к границе расширения, а не к удалённому пользовательскому вводу.

Правка: передавать `deepFreeze(structuredClone(info))`, сделать контракт глубоко readonly. Проверить мутации termination, consensus и evaluation, включая вложенные массивы. Объект события также общий для всех `EventLog` listeners: стоит замораживать snapshot перед уведомлением, чтобы наблюдатели не меняли данные, получаемые следующими наблюдателями.

### 6. Major, условие — сбой финальной записи: recovery заменяет уже записанный SUCCESS на INTERRUPTED

Код: `src/experiment/runner.ts:775`, `src/experiment/service.ts:93`.

Нормальный `finish` сначала пишет `experiment_finished`, а потом отдельным запросом обновляет строку experiments. Ошибка записи или завершение процесса между операциями оставляет terminal event без terminal row. Recovery считает такой запуск прерванным и дописывает другой финал.

Подтверждение: временный SQLite trigger, имитирующий отказ финального UPDATE, дал:

```text
до recovery:    events=[SUCCESS],             experiments.outcome=null
после recovery: events=[SUCCESS, INTERRUPTED], experiments.outcome=INTERRUPTED
```

Последствие: сохранённый успешный исход теряется в summary, запуск исключается из success rate. Тест атомарности самого recovery уже есть; нормальный путь завершения остаётся неатомарным.

Правка: terminal event и terminal row сохранять в одной транзакции, уведомлять подписчиков после commit. Recovery сделать идемпотентным: если валидный terminal event уже существует, восстанавливать summary и row по нему. Не подавлять отказ `started.done` в batch без отражения в статусе batch.

## Архитектурные ограничения

- В одном процессе совмещены API, SQLite-записи, LLM orchestration и extensions. HTTP-crash поэтому затрагивает все эксперименты. Исправить обработчик нужно немедленно; отдельный worker для исполнения полезен при переходе от локального стенда к длительным платным сериям.
- Extension hook ожидается без общего watchdog. Дополнение, игнорирующее abort и не завершающее Promise, может удержать run навсегда. Типы и замораживание объектов не обеспечивают изоляцию отказов исполнения; нужны ограниченные по времени hooks и явная политика завершения.
- Каждый prompt снова содержит историю, которая затем целиком сохраняется в trace. При постоянном размере новых сообщений суммарные prompt tokens и объём trace растут примерно квадратично с числом ходов. Нужна явная политика контекстного окна и ограничения объёма; её следует фиксировать как экспериментальный параметр.
- `BudgetTracker` измеряет elapsed через `Date.now`; перевод системных часов влияет на время запуска и лимиты. Для длительностей нужен монотонный clock, для timestamp событий — календарное время.
- Факты в текстах агентов и численные параметры evaluator редактируются независимо. Валидатор проверяет форму обоих, но не согласованность смысла. Изменение `evaluator.params` в batch может создать задачу, о новых правилах которой агентам не сообщили. Лучше генерировать prompts и evaluator params из одной параметризованной task instance.

## Методологические ограничения

### Success rate смешивает автономные и управляемые запуски

`src/batch/aggregate.ts:74` исключает только статус `ABORTED`. Запуск, которому оператор выбрал следующего агента или принудительно завершил обсуждение, остаётся в основной rate при успешном завершении. Количество `intervened` показывается отдельно, но знаменатель не меняется.

Предложение: отдельно считать autonomous rate и assisted rate; для исследований по умолчанию использовать автономную выборку. Наличие флага в CSV помогает последующему анализу, но не исправляет смешанную агрегированную оценку.

### Ошибки провайдера могут быть неслучайными пропусками

Текущая rate корректно описывает успех среди evaluable runs. Она не равна вероятности успешного запуска с первой попытки: длинные, дорогие или специфичные для модели запросы могут чаще завершаться `PROVIDER_ERROR`. Их исключение может менять сравнение моделей или условий. Исключения видны в UI, поэтому проблема не в сокрытии ошибок, а в интерпретации.

Предложение: одновременно публиковать operational success по всем попыткам, conditional success по evaluable и долю infrastructure failures. Ретраи завершённых запусков планировать заранее и учитывать отдельно.

### Interleaved не является рандомизацией

`src/batch/spec.ts:94` повторяет условия в одном и том же порядке. Это уменьшает грубый временной дрейф, но не устраняет эффект позиции, нагрузки и взаимного влияния через общий request gate. Ожидание gate входит в active time и расходует time limit; изменение batch concurrency способно менять исход при одинаковом configHash.

Предложение: seeded randomization внутри блоков, балансировка позиции условий, запись seed и фактического порядка. Для latency-сравнений показывать provider time и queue wait отдельно; фиксировать concurrency и request gate в идентификаторе экспериментального окружения.

### Успех задачи ещё не доказывает пользу координации

Stub-агенты — scripted fixtures; их успех подтверждает проводку протокола. Повторение одного фиксированного задания на LLM оценивает вариативность в этой задаче, а не переносимость на новые задачи. Wilson interval по таким повторениям не описывает неопределённость обобщения на распределение задач.

Предложение: набор task instances с проверенными решениями и контролями: один агент со всей информацией, один агент с частичной информацией, несколько агентов без общения, разные разбиения фактов, перестановка ролей/первого говорящего/proposer. Сравнивать при согласованных ресурсных бюджетах.

### Протокол сам меняет наблюдаемое поведение

Принудительные readiness rechecks, фиксированный proposer, blind voting и форматные retries — содержательные условия эксперимента. В hybrid два агента могут выбирать друг друга без гарантии слова остальным; least-recent fallback действует лишь при отсутствии usable explicit/classifier выбора. Это не обязательно ошибка: всё зависит от исследуемого протокола.

Предложение: сохранять эти режимы как параметры, отдельно измерять распределение ходов, долю непроизнесённых закрытых фактов, повторения, veto и расхождения между consensus и correctness. Fairness-ограничения маршрутизации вводить явно, поскольку они меняют исследуемый механизм.
